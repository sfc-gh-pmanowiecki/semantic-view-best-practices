Core Concepts

Foundational knowledge required before working with semantic views

Logical vs Physical Table Names

Semantic views define logical names that map to physical database tables. Generated SQL always uses physical table names — this is correct and expected.

YAML
tables:
  - name: SALES_FACT         # logical name
    base_table:
      database: PROD
      schema:   SALES
      table:    TBL_SALES    # physical table
ℹ️ Generated SQL referencing prod.sales.tbl_sales (not SALES_FACT) is correct — never flag it as an issue.
Physical vs Computed Elements

The semantic model mixes physical database columns with computed elements you define.


ElementTypeCan Add?
DimensionsPhysical columnsNo
FactsPhysical numeric columnsNo
Time DimensionsPhysical date/time columnsNo
MetricsCalculated aggregationsYes
FiltersNamed WHERE clausesYes
RelationshipsTable joinsYes
Custom InstructionsLLM guidanceYes

Add vs Enhance

Understanding what operations are allowed on each element type

Cannot Add (Physical Columns)

Dimensions and facts correspond to real columns in Snowflake tables. You cannot invent new ones. You can only enhance their metadata.


You CAN enhance with:

  • descriptions — rich business context
  • synonyms — alternative user phrasings
  • sample_values — representative data examples
  • unique flag — prevent unnecessary DISTINCT
  • data_type — explicit type annotation
Can Add (Computed Elements)

These elements exist only in the semantic model and don't need corresponding physical columns.


  • Metrics — aggregations like SUM(amount), COUNT(DISTINCT id)
  • Filters — named WHERE conditions like ACTIVE_CUSTOMERS
  • Relationships — join definitions between tables
  • Custom/Module Instructions — natural language guidance for the LLM
  • Verified Queries — gold-standard NL→SQL pairs
🚫

Deprecated Fields

Fields that must never appear in any semantic view YAML

⚠️ Using deprecated fields will cause validation failures or silently produce wrong results. Always check generated YAML for these before deploying.
✗
default_aggregation
Deprecated on both Dimension (proto line 84) and Fact (proto line 192). Use explicit metrics with an expr instead.
✗
measures
Old terminology. Use facts for physical numeric columns.
✗
one_to_many, many_to_many
Deprecated relationship types. Use one_to_one or many_to_one only.
✗
full_outer, cross, right_outer
Deprecated join types. Only inner and left_outer are valid.

Always attempt fixes in this order — custom instructions are the last resort

  • 1

  • 2

Dimension & Fact Enhancement

Improve metadata on existing physical columns — cannot add new ones

Rich Descriptions Strategy

A description should answer what the column is, how it's used, and provide business context — not just restate the column name.

✗ Weak description
- name: ACCOUNT_ID
  description: Account ID
  expr: account_id
  data_type: NUMBER(38,0)
✓ Rich description
- name: ACCOUNT_ID
  description: "Unique identifier for Snowflake
    accounts. Used to track usage
    and link customer information.
    Commonly used for account-level
    analysis."
  expr: account_id
  data_type: NUMBER(38,0)
  unique: true
Synonyms for Term Matching

Add alternative terms users might phrase in natural language — business jargon, abbreviations, common alternatives, and domain-specific names.

YAML
- name: SALESFORCE_ACCOUNT_NAME
  description: "Official account name as recorded in Salesforce CRM"
  expr: salesforce_account_name
  synonyms:
    - company name
    - customer name
    - account name
    - client name
    - org name
ℹ️ Synonyms are not required — but they significantly improve NL→SQL matching when users phrase questions differently than the column name.
Unique Flag

Mark columns whose values are unique (primary keys, IDs) to prevent the LLM from generating unnecessary DISTINCT in aggregations.

YAML
- name: USER_ID
  description: "Unique identifier for each user account"
  expr: user_id
  data_type: NUMBER(38,0)
  unique: true    # signals no DISTINCT needed when counting this column
Full Before / After Example
✗ Before — minimal metadata
dimensions:
  - name: STATUS
    description: Status
    expr: status
    data_type: VARCHAR
✓ After — rich metadata
dimensions:
  - name: STATUS
    description: "Account lifecycle status.
      ACTIVE = paying and using,
      TRIAL = evaluation period,
      CHURNED = cancelled."
    expr: status
    data_type: VARCHAR
    synonyms: [account status, state]
    sample_values:
      - ACTIVE
      - TRIAL
      - CHURNED

Metrics

Calculated aggregations you add on top of physical fact columns

💡 Facts vs Metrics: Facts are raw numeric columns (cannot add). Metrics are derived aggregations you define (can add freely).
Metric Structure
YAML
metrics:
  - name: DESCRIPTIVE_METRIC_NAME
    description: "What it calculates and when to use it"
    expr: AGGREGATE_EXPRESSION
    access_modifier: public_access    # always required
Count Distinct
- name: UNIQUE_CUSTOMERS
  description: "Distinct customer count"
  expr: COUNT(DISTINCT customer_id)
  access_modifier: public_access
Total Revenue
- name: TOTAL_REVENUE
  description: "Sum of all order amounts"
  expr: SUM(order_amount)
  access_modifier: public_access
Average Order Value
- name: AVERAGE_ORDER_VALUE
  description: "Average value per order"
  expr: AVG(order_amount)
  access_modifier: public_access
Common Mistakes
  • ❌ Using default_aggregation (deprecated — use explicit metrics)
  • ❌ Non-aggregate expressions in metrics (must use SUM, COUNT, AVG, etc.)
  • ❌ Missing access_modifier field
  • ❌ Vague descriptions — the LLM needs to understand when to apply this metric
  • ❌ Overly complex one-liner expressions — break complex logic into steps
🔽

Filters

Named WHERE conditions that encapsulate reusable business logic

⚠️ Filters must be nested under the table they apply to — not at the top level of the model.
Filter Structure
YAML
tables:
  - name: TABLE_NAME
    filters:
      - name: DESCRIPTIVE_FILTER_NAME
        description: "When and how to use this filter"
        expr: WHERE_CLAUSE_EXPRESSION
Time-based Filter
- name: LAST_30_DAYS
  description: "Records from last 30 days"
  expr: date >= DATEADD(
    day, -30, CURRENT_DATE())
Business Logic Filter
- name: ACTIVE_CUSTOMERS
  description: "Active customer status"
  expr: status = 'ACTIVE'
    AND last_purchase_date
    >= DATEADD(month, -6,
        CURRENT_DATE())
Categorical Filter
- name: VALID_TRANSACTIONS
  description: "Completed & verified only"
  expr: transaction_status
    = 'COMPLETED'
    AND is_verified = TRUE
Common Mistakes
  • ❌ Placing filters at the model top level instead of under their table
  • ❌ Using HAVING clauses — filters are WHERE-style expressions only
  • ❌ Filters that depend on aggregations — those belong in metrics
  • ❌ Missing descriptions — the LLM needs to know when to activate the filter

Relationships

Join definitions between tables — requires verified primary keys

⚠️ PK required: At least one table in the join must have a verified primary key. Never add PKs without verifying ≥95% uniqueness via infer_primary_keys.py or explicit user confirmation.

Relationship Structure (Single & Composite Keys)
YAML
relationships:
  - name: ORDERS_TO_CUSTOMERS
    left_table:  ORDERS
    right_table: CUSTOMERS
    relationship_columns:
      - left_column:  CUSTOMER_ID
        right_column: CUSTOMER_ID
    relationship_type: many_to_one
    join_type:        left_outer

  # Composite key example:
  - name: USAGE_TO_ACCOUNTS
    left_table:  USAGE
    right_table: ACCOUNTS
    relationship_columns:
      - left_column:  ACCOUNT_ID
        right_column: ACCOUNT_ID
      - left_column:  DEPLOYMENT
        right_column: DEPLOYMENT
    relationship_type: many_to_one
    join_type:        left_outer

Custom Instructions

LLM guidance — use only when semantic model elements cannot express the logic

🚨 Last resort only. First try: Dimensions → Metrics → Relationships → Filters → Descriptions. Only add instructions when none of the above can solve the problem.
When It's Appropriate
  • Snapshot/historical data — always filter for current snapshot by default
  • Aggregation interpretation — "biggest X" means frequency not value
  • Domain-specific rules — fiscal calendar offsets, special status mappings
  • Query patterns — when GROUP BY guidance is needed
Module vs Model Level

Prefer module_custom_instructions (targeted) over custom_instructions (global).

module_custom_instructions:
  sql_generation: |-
    Use table aliases for readability.
  question_categorization: |-
    Treat trend questions as
    UNAMBIGUOUS_SQL.
ℹ️ If neither type exists yet, create module_custom_instructions. If custom_instructions already exists, extend it rather than mixing types.
✗ Query-specific (overfitting)
custom_instructions: |-
  For "Who are biggest partners?",
  use COUNT(DISTINCT id)
  GROUP BY partner.
✓ Generalized (correct)
custom_instructions: |-
  "Biggest [dimension]" means most
  frequent:
  - GROUP BY dimension
  - COUNT(DISTINCT primary_key)
  - Filter out NULLs
  Examples: "biggest partners"
    → COUNT GROUP BY partner
Real-world Examples
custom_instructions: |-
  Unless explicitly asked for historical analysis,
  ALWAYS filter for snapshot_flag = 'Current'.
custom_instructions: |-
  For fiscal quarters, add 11 months before
  extracting the quarter number.
  The fiscal year starts in February.
custom_instructions: |-
  "Biggest X" where X is categorical means
  frequency (COUNT), not value (SUM),
  unless the question explicitly mentions
  revenue or ACV.

Best Practices Audit

Four checks run during a best-practices audit: documentation, naming, metadata, and type safety

1 · Documentation Checks
Error
Missing table description
Every table must have a description field
Error
Missing column description
All dimensions, facts, and metrics need descriptions
Warning
Low-quality description
Description merely restates the column name with no added context
2 · Naming Convention Checks
Warning
Special characters in names
Element names should use alphanumeric + underscores only
Info
Inconsistent naming style
Mix of casing styles (e.g., camelCase vs UPPER_SNAKE_CASE)
3 · Metadata Completeness
Warning
Missing data types
data_type should be defined on all dimension and fact columns
Info
Relationship descriptions present
Relationships should not have descriptions — they add noise
4 · Type Safety Checks
Error
Date column classified as dimension
Date/timestamp columns should be time_dimensions, not plain dimensions
Error
Wrong dimension/measure classification
Numeric columns suitable for aggregation should be facts, not dimensions

Inconsistency Detection

Conflicts and logical errors that make the model confusing or produce wrong results

Critical
Will cause query failures or wrong results
Example: Conflicting metric definitions computing the same KPI differently in two places
High
Likely to cause confusion
Example: A dimension described as "customer" in one table and "user" in another for the same concept
Medium
May cause issues in specific scenarios
Example: Filter referencing a column not present in the table it's attached to
Low
Stylistic inconsistencies
Example: Some metrics have access_modifier while others don't
🔁

Duplicate Detection

Redundant information that wastes tokens and confuses the LLM

Exact Duplicates

An instruction or description verbatim repeats information already in the semantic model structure itself.

✗ Remove entirely — the model already conveys this.
High Similarity (>85%)

Two instructions or descriptions convey essentially the same information in different wording.

✗ Merge into one consolidated instruction.
Partial Overlap

An instruction partially covers ground already expressed in a metric/filter/dimension description.

ℹ️ Review and trim redundant portion, keeping only what adds new context.

Creation Workflow

FastGen-based automated semantic view generation from SQL queries and table metadata

⚠️ Never generate SQL queries on your own to feed FastGen. Always wait for the user to provide SQL, table references, or business context.
1
Context Gathering
Collect semantic view name, target database/schema, and SQL context (queries, table FQNs, or business description). Mandatory stop until user provides this.
2
FastGen Execution
Build request JSON → call SYSTEM$CORTEX_ANALYST_FAST_GENERATION(...) → store query ID → extract YAML with pagination via RESULT_SCAN. Falls back to manual creation if FastGen fails.
SQL
SELECT SYSTEM$CORTEX_ANALYST_FAST_GENERATION(...)
SET fastgen_query_id = (SELECT LAST_QUERY_ID())
SELECT * FROM RESULT_SCAN($fastgen_query_id)
3
Review & Validate
Inspect generated YAML (tables, relationships, VQRs, warnings). Run SYSTEM$CREATE_SEMANTIC_VIEW_FROM_YAML(..., TRUE) in verify-only mode. Fix any schema/relationship/syntax issues and re-validate until clean.
SQL
CALL SYSTEM$CREATE_SEMANTIC_VIEW_FROM_YAML(
  'TARGET_DB.SCHEMA',
  $$
  -- full YAML content here
  $$,
  TRUE   -- verify-only mode
);
4
Optional Enhancement
Enrich primary keys and relationships using infer_primary_keys.py (≥95% uniqueness threshold) and relationship_creation.py.
5
Next Steps
Choose: run Audit Mode → Debug Mode → Deploy to Snowflake → Manual refinement with semantic_view_set.py.

Audit Modes

Four specialized audit types available after semantic view setup

1VQR Testing (Behavioral)

Tests natural language queries against the semantic view without VQR hints. Validates whether the model independently generates correct SQL — identifies where the model needs improvement.

2Best Practices Audit

Checks documentation completeness, naming conventions, metadata, type safety, inconsistencies, duplicates, and missing relationships. Reports with ERROR / WARNING / INFO severity.

3Custom Criteria

User-defined validation rules evaluated against the semantic view. Allows domain-specific compliance checks not covered by built-in best practices.

4SVA VQR Compile Check

Validates that VQR SQL compiles correctly against the model using validate_verified_queries via SYSTEM$CORTEX_ANALYST_SVA_TOOL. Per-query valid / error_detail output.

ℹ️ This is not the same as VQR Testing (mode 1). Mode 1 = behavioral NL→SQL; Mode 4 = SQL compilation check.
📝

Verified Queries (VQRs)

Gold-standard natural language → SQL pairs that teach the model correct behavior

VQR Structure
YAML
verified_queries:
  - name: monthly_active_users
    question: "How many active users per month?"
    sql: |-
      SELECT
        DATE_TRUNC('month', logged_at) AS month,
        COUNT(DISTINCT user_id)        AS active_users
      FROM prod.analytics.usage_logs
      WHERE logged_at >= '2024-01-01'
      GROUP BY 1
      ORDER BY 1
    verified: true
VQR Generation Sources

The vqr_suggestions workflow mines two data sources in parallel:


  • Cortex Analyst usage history — real user NL questions with generated SQL
  • Snowflake query history — SQL patterns from ACCOUNT_USAGE.QUERY_HISTORY

Results from both are merged, deduplicated, and ranked before presenting to the user for approval.

⚠️ Always use semantic_view_set.py to apply VQR changes — never edit verified_queries manually in the YAML.
VQR Validation (Compile Check)

Use SYSTEM$CORTEX_ANALYST_SVA_TOOL with validate_verified_queries to confirm every VQR SQL compiles against the model before deploying.

SQL
SELECT SYSTEM$CORTEX_ANALYST_SVA_TOOL(
  OBJECT_CONSTRUCT(
    'tool',               'validate_verified_queries',
    'semantic_view_name',  'DB.SCHEMA.MY_VIEW',
    'warehouse',           'MY_WAREHOUSE'
  )
);

Returns per-query results with valid: true/false and error_detail for any compilation failures.

Key Principles Summary

Rules that apply across every workflow in the skill

Test Locally First

Always test changes against a local YAML file using the semantic_model_file parameter. Only upload to Snowflake when the user explicitly requests deployment.

Mandatory Approval Checkpoint

Before applying any optimization, wait for explicit user approval ("approved", "looks good", "proceed"). Never chain multiple separate optimizations without approval between them.

Use Approved Tools Only

All YAML operations must go through semantic_view_get.py (read) and semantic_view_set.py (write). Never hand-edit the YAML directly.

Prefer Explicit Over Instructions

Explicit model elements (metrics, filters, relationships) are always preferred over custom instructions. Instructions are for logic that cannot be expressed structurally.

Validate After Each Change

Run cortex reflect <file.yaml> after every optimization. Iterate until validation passes before presenting results to the user.

Always Use uv run python

Scripts must be executed with uv run python script.py. Never use python or python3 directly — environment dependencies may not be available.
